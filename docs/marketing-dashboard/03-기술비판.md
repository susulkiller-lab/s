## 3. 권장 데이터 모델 수정안

```
경로                          쓰기              주요 필드
config/main                   owner             holidays, weekFocus (판별표·기준값은 코드 상수)
tasks/{taskId}                owner             title, channel, versions[{from, kind, qty, due, assignee}], pauses[], endAt
members/{uid}                 owner             name(팀 내 호칭), order, active
specials/{id}                 interact          title, source, due, qty, status, done{키:{by, at, day}}
logs/{uid}/w/{2026-W44}       본인, owner       week, entries{키:{t, day, at, n, url, title, ch}}, skips{업무_날짜:{why}}
inq/{2026-10}/items/{id}      interact(읽기도)  day, hour, type, path, term, landing, field, review, followUp, memo, by
weeks/{2026-W44}              owner             memo, closed{업무별 목표·완료, 발행 수, 문의 수}
```

```json
{"db": {"rules": [
  {"path": "", "read": "view", "write": "interact"},
  {"path": "config", "write": "owner"},
  {"path": "tasks", "write": "owner"},
  {"path": "members", "write": "owner"},
  {"path": "weeks", "write": "owner"},
  {"path": "logs", "read": "view", "write": "owner"},
  {"path": "logs/{self}", "write": "interact"},
  {"path": "inq", "read": "interact", "write": "interact"}
]},
 "user": {"scopes": ["profile"]},
 "downloads": {}}
```

- 규칙: db.d.ts에 따라 {self}의 접두 경로(logs)에는 read와 write를 모두 적어야 게시됩니다. read를 view로 열어 서로의 기록을 읽게 하고, write를 owner로 두어 남의 기록은 소유자만 고치게 합니다(소급·정정 담당).
- 저장: 주 문서는 처음 한 번만 set으로 만들고, 이후에는 update({entries:{키: 항목}})로 병합합니다. 빼기는 해당 키를 {void:true}로 바꿉니다. 같은 문서에는 한 번에 하나씩 쓰고 연속 체크는 묶어 저장합니다.
- 계산과 중복: 완료 수는 entries에서 업무별 n을 더해 구하고, 날짜별 배정은 저장하지 않고 읽을 때 계산합니다. 같은 정규화 키는 덮어쓰여 한 번만 셉니다. 팀원 사이의 중복은 구독 중인 14주 범위에서 확인 화면이 걸러 내므로 array-contains 조회가 필요 없습니다. 지난주 기록은 closed가 생기기 전까지만 받습니다.
- 규모(가정: 5명, 월 문의 100건): 연 문서 약 1,750개(초안 약 2,700개). 첫 화면 읽기는 logs 70개와 설정류 약 45개, 구독은 약 11개입니다.
- 예외: 게시 첫날 user.id()가 null인 팀원이 있으면 logs/{memberId}-{주}(interact 쓰기) 평면 구조로 바꾸고, 2번 위험은 그대로 감수합니다.
